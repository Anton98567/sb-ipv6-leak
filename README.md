# sb-ipv6-leak

Проверка и устранение **утечки IPv6** в клиентских конфигах [sing-box](https://sing-box.sagernet.org).

## Проблема

TUN-инбаунд с адресом **только IPv4** захватывает маршрут одного семейства:

```json
"inbounds": [{ "type": "tun", "address": ["10.0.0.1/28"], "auto_route": true, "strict_route": true }]
```

На dual-stack устройстве клиента (телефон/ПК с рабочим IPv6 от провайдера) IPv6-трафик
**не попадает в туннель** и уходит напрямую — сайты видят реальный IPv6-адрес пользователя.
Это классическая «утечка IPv6»: прокси работает, IPv4 «в туннеле», а IPv6 — нет.

Смежные векторы той же природы:

* `auto_route: false` — захвата маршрутов нет вообще, мимо туннеля уходит всё;
* `strict_route: false` — ОС (особенно Android/Windows) может строить обходные маршруты.

## Что делает патч

В TUN-инбаунд добавляется IPv6-CIDR (ULA `fdfe:dcba:9876::1/64`, значение из примеров
документации sing-box) и принудительно включаются `auto_route`/`strict_route`:

```json
"inbounds": [{ "type": "tun", "address": ["10.0.0.1/28", "fdfe:dcba:9876::1/64"],
               "auto_route": true, "strict_route": true }]
```

Теперь туннель захватывает оба семейства: IPv6 идёт через прокси и выходит с IP сервера.
Ссылки и пароли конфигов **не меняются** — клиенты подхватывают правку при обновлении
подписки или переимпорте конфига.

Патчится только TUN-инбаунд, остальная часть конфига не изменяется. Патч идемпотентен.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/Anton98567/sb-ipv6-leak/main/install.sh | bash
```

Или просто скачать `sb-ipv6-leak.sh` и дать ему права на исполнение. Требуются
`bash`, `jq` и `curl`; для режимов `test config` / `test tun` — бинарник `sing-box` в PATH.

## Использование

```bash
# найти конфиги и показать векторы утечки (авто-поиск в /var/www)
sb-ipv6-leak check

# то же, но в конкретном каталоге
sb-ipv6-leak check /etc/sb-configs

# сводка: что пропатчено, что нет
sb-ipv6-leak status

# применить патч ко всем конфигам с утечкой (+ бэкап)
sb-ipv6-leak patch

# откат: убрать добавленный IPv6 из TUN
sb-ipv6-leak remove
```

Сквозной тест «что видит мир» (без правки файлов):

```bash
# через готовый прокси (HTTP или SOCKS5)
sb-ipv6-leak test proxy http://127.0.0.1:10808

# через клиентский конфиг: поднимается временный mixed-инбаунд на 127.0.0.1:18080,
# маршруты машины НЕ трогаются
sb-ipv6-leak test config ORDER-1-TRJ-CLIENT.json

# полный тест в TUN-режиме — перехватывает весь трафик машины!
# только на VPS/тестовом стенде, подтверждение --yes обязательно
sb-ipv6-leak test tun ORDER-1-TRJ-CLIENT.json --yes
```

Пример вывода:

```
=== прямой выход (без туннеля) ===
  IPv4: 192.0.2.10
  IPv6: 2001:db8::10
=== через туннель ===
  IPv4-цели видят: 198.51.100.7
  IPv6-only цель видит: 2001:db8::7
---
✅ IPv4 идёт через туннель (видимый IP: 198.51.100.7)
✅ IPv6 идёт через туннель (видимый IP: 2001:db8::7)
```

Если вместо IP туннеля виден прямой IP — это утечка, лечится `patch` + переимпорт конфига.

## Возврат изменений

Перед патчем исходные файлы копируются в `$BAK_ROOT/leakfix-<дата>/`
(по умолчанию `/root/bak-template/leakfix-<дата>/`) — восстановление простым
копированием обратно. Либо `sb-ipv6-leak remove` убирает добавленный CIDR
(`auto_route`/`strict_route` при этом остаются включёнными — это безопаснее).

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SB_DIR` | `/var/www` | каталог для авто-поиска конфигов |
| `TUN_IPV6` | `fdfe:dcba:9876::1/64` | IPv6-CIDR, добавляемый в TUN |
| `BAK_ROOT` | `/root/bak-template` | каталог бэкапов |
| `SINGBOX_BIN` | `sing-box` | путь к бинарнику sing-box |

## Замечания

* Патч рассчитан на конфиги sing-box JSON (формат `address`-массив, sing-box 1.11+).
* Системный DNS (`type: local` без `detour`) в правилах прямого доступа — норма:
  прямые домены резолвятся локально намеренно; проксируемый трафик должен ходить
  через DNS-сервер с `detour` (например, DoT/DoH через туннель) — `check` показывает
  количество таких серверов справочно.
* После патча клиентам нужно **обновить подписку / переимпортировать конфиг**.
* `test tun` меняет маршрутизацию всей машины до завершения процесса — используйте
  только на одноразовых VPS/стендах.
